## 1. Identity Mapping Strategy

### 1.1 The Core Problem

WarriorPlus is a **marketplace**, not a checkout provider like Dodo. The buyer:
1. Discovers RobinOS via a WarriorPlus Marketplace listing
2. Pays WarriorPlus directly (on WarriorPlus's checkout page, not RobinOS's)
3. WarriorPlus sends an **IPN (Instant Payment Notification)** to a registered RobinOS endpoint
4. RobinOS must identify **which user just paid** and grant them access

There is **no opportunity** for RobinOS to pre-create a checkout session with metadata — the entire transaction happens on WarriorPlus's side. This is fundamentally different from Dodo, where RobinOS creates the checkout session and embeds metadata.

### 1.2 Candidate Approaches

#### Option A: Email Matching
- **Mechanism:** Match the buyer email in the IPN payload to a RobinOS `profiles.email`
- **Pros:**
  - Zero friction — buyer uses the same email they used on RobinOS
  - Works for users who already have a RobinOS account
  - Works for guest purchases (account created post-purchase using email)
- **Cons:**
  - **Spoofing risk** — anyone who knows a user's email could buy on WP and get them credited
  - **Email collision** — if two accounts share an email (rare but possible), ambiguity
  - **Privacy** — exposing which users have WP purchases via email lookup
  - **Case sensitivity** — emails must be normalized (lowercase + trim)

#### Option B: Signed User ID in URL Params
- **Mechanism:** When a logged-in RobinOS user clicks "Buy via WarriorPlus", generate a signed URL like `https://warriorplus.com/oops/...?rbin_uid=<uuid>&rbin_sig=<hmac>&rbin_exp=<timestamp>` containing the user's ID + HMAC signature + expiry
- **Pros:**
  - **Cryptographically strong** — HMAC proves the URL was generated by RobinOS
  - **Tamper-evident** — any modification breaks the signature
  - **Time-bounded** — expiry prevents replay
  - **Direct mapping** — no email lookup needed
  - **Zero ambiguity** — user ID is unique
- **Cons:**
  - **Only works for logged-in users** — guest buyers have no `user_id` to sign
  - **Requires RobinOS frontend involvement** — user must start the purchase from RobinOS
  - **WarriorPlus must preserve URL params through their checkout** — typically they do, but the params may be stripped during redirect
  - **The signature is from WarriorPlus's perspective** — WarriorPlus may strip unrecognized params

#### Option C: Claim Token (Post-Purchase)
- **Mechanism:** After a purchase, the buyer lands on a "Claim Your Account" page. They enter their email + a purchase token (or just email — RobinOS looks up recent WP purchases by email). RobinOS creates/links the account.
- **Pros:**
  - **No trust assumptions** — buyer explicitly claims the purchase
  - **Works for guests** — account is created during claim
  - **Audit-friendly** — claim event is logged
- **Cons:**
  - **Manual step** — buyer must take action, increasing drop-off
  - **Email-only trust** — same spoofing risk as Option A
  - **Time-window** — purchases must remain unclaimed for a window (e.g. 30 days)
  - **Lost purchases** — buyer who closes the tab forgets to claim

#### Option D: Manual Linking (Admin Intervention)
- **Mechanism:** All WP purchases land in a "pending identity resolution" queue. Admin manually matches each purchase to a user (or creates a new account).
- **Pros:**
  - **100% certainty** — no spoofing possible
  - **No automation risk**
- **Cons:**
  - **Doesn't scale** — manual queue grows linearly with WP sales
  - **Delay** — buyer waits hours/days for access
  - **Operational burden** — requires admin attention for every sale
  - **Bad UX** — buyers will complain

### 1.3 Recommended Approach: Hybrid (B + A + C)

**Primary: Signed user_id with email verification (Option B + A combined)**

The RobinOS "Buy via WarriorPlus" button generates a signed URL:

```
https://warriorplus.com/oops/a/b/c/
  ?rbin_uid=<user_uuid>
  &rbin_email=<sha256(email)>
  &rbin_exp=<unix_timestamp>
  &rbin_sig=<hmac_sha256(uid + email + exp, secret)>
```

**Critical assumption:** WarriorPlus **preserves URL query parameters** through their checkout flow. This is standard practice for affiliate networks, but must be confirmed via test purchase.

**Why this works:**
- Logged-in users get a **cryptographically strong** identity binding (signed `user_id`)
- The signed `email` hash serves as a **redundant verification channel** — if WarriorPlus strips `rbin_uid` but preserves `rbin_email`, we can still identify the user via email lookup
- The expiry prevents **replay attacks** — same URL cannot be reused after 1 hour

**Secondary: Email matching with rate limiting (Option A for fallback)**

If neither signed param survives:
- IPN arrives with buyer email
- Match `profiles.email` (lowercased, trimmed) to buyer email
- If matched → credit the user
- If not matched → **rate limit** (max 3 unmatched purchases per email per 24h to prevent spam)

**Tertiary: Claim token fallback (Option C)**

If email match also fails (e.g. buyer used a different email on WP):
- Create a `warriorplus_pending_claims` table row with a **claim token** (UUID v7)
- Send a "Claim Your Purchase" email to the WP buyer email
- Buyer clicks link → enters the email they used on RobinOS → if emails match a recent claim, link is approved
- Claim tokens expire after **30 days**

**Why not Option D (manual):** Manual linking doesn't scale and creates customer satisfaction issues. Only use for edge cases (e.g. buyer disputes identity).

### 1.4 Identity Resolution Priority

```
1. Signed rbin_uid (verified HMAC + not expired) → user_id = rbin_uid
2. Signed rbin_email hash → lookup by email hash
3. Plaintext buyer_email in IPN → lookup by profiles.email (rate-limited)
4. No match → create warriorplus_pending_claims row, email claim token
5. Manual admin intervention (last resort)
```

### 1.5 Trust Levels

| Source | Trust Level | Action |
|--------|-------------|--------|
| Signed `rbin_uid` | **High** (cryptographic) | Direct grant |
| Signed `rbin_email` hash | **High** (cryptographic) | Email match |
| Plaintext `buyer_email` in IPN | **Medium** (spoofable) | Rate-limited match |
| Claim token via email link | **Medium** (self-attested) | Manual approval |
| Admin manual link | **High** (human verified) | Direct grant |

## 2. Checkout Flow

### 2.1 The Fundamental Difference from Dodo

With Dodo, the flow is:
```
RobinOS frontend → RobinOS Edge Function → Dodo SDK → Dodo checkout → Webhook
```

With WarriorPlus, the flow is:
```
RobinOS frontend → Signed URL → WarriorPlus Marketplace → WarriorPlus checkout → IPN
```

RobinOS does **not** create a checkout session. WarriorPlus owns the checkout. RobinOS only:
1. Generates a signed redirect URL
2. Receives IPN notifications
3. Grants entitlements

### 2.2 Step-by-Step Flow

#### Step 1: User Initiates Purchase from RobinOS

User is logged in to RobinOS and clicks "Buy via WarriorPlus" (or a similar CTA). The CTA appears:
- On `/pricing` page as an alternative payment method
- On `/warriorplus` sales page (when `warriorplus_page_enabled = true`)
- In the Upgrade Dialog when other providers are unavailable

#### Step 2: Frontend Requests Signed URL

Frontend calls a new Edge Function `warriorplus-build-link` (analogous to `create-checkout`):

```
POST /functions/v1/warriorplus-build-link
Body: { planKey: "creator", userId: "...", userEmail: "...", referralCode: "ABC123" }
```

The Edge Function:
1. Authenticates user via JWT
2. Validates plan key
3. Checks for duplicate active subscription (same logic as Dodo: `provider='warriorplus' + plan=X + status=active → 409`)
4. Generates a signed URL with:
   - `rbin_uid` = user.id
   - `rbin_email` = sha256(lowercase + trim of email)
   - `rbin_exp` = now + 1 hour (UNIX timestamp)
   - `rbin_sig` = HMAC-SHA256 of (uid + ":" + email_hash + ":" + exp, secret)
   - `rbin_ref` = referralCode (if present) — for WP affiliate tracking
5. Returns `{ signedUrl, expiresAt }`

#### Step 3: User Redirected to WarriorPlus

Frontend does `window.location.href = signedUrl`.

WarriorPlus's checkout page receives the URL. **Assumption:** WarriorPlus preserves query params through their checkout flow.

#### Step 4: User Pays on WarriorPlus

Buyer enters payment details on WarriorPlus's checkout. WarriorPlus processes the payment.

#### Step 5: WarriorPlus Sends IPN

Immediately after payment, WarriorPlus POSTs to RobinOS's IPN endpoint. See §3 for IPN details.

#### Step 6: User Lands on Return URL

WarriorPlus redirects buyer to a configured **thank-you URL**. RobinOS provides this URL during WarriorPlus Marketplace registration:
```
https://tryrobin.xyz/warriorplus/thank-you?txn=<wp_txn_id>
```

The thank-you page:
1. Shows "Your purchase is being processed"
2. Polls `get_subscription_status` every 2 seconds (up to 30s)
3. When status becomes active, redirects to dashboard
4. If still pending after 30s, shows "processing — you'll receive an email when ready"

#### Step 7: RobinOS Processes IPN Asynchronously

The IPN handler runs in parallel. Even if the user is on the thank-you page, the IPN is being processed. By the time the user lands on the dashboard (manual refresh or after 30s polling), entitlements are usually already active.

### 2.3 Edge Cases

#### Logged-out User Clicks "Buy via WarriorPlus"
- Frontend requires login before allowing the CTA
- "Please log in or create an account first" message
- After login, redirect to the same purchase flow

#### User Has Existing Dodo Subscription
- Frontend checks `get_subscription_status` before showing CTA
- If user has active Dodo sub, show "You already have an active subscription. Manage from Settings."
- If user wants to switch providers, they must cancel Dodo first (or use Dodo's customer portal)

#### User Buys on WarriorPlus Without Clicking RobinOS Button
- User finds RobinOS on WP Marketplace directly (e.g. via WP affiliate link)
- IPN arrives with only buyer_email (no signed params)
- Falls back to Option A (email match) → Option C (claim token)
- See §1.4 priority chain

#### Duplicate Click (User Clicks Twice)
- Second click generates a new signed URL with a fresh exp
- User may end up buying twice on WP
- RobinOS receives two IPNs
- Idempotency prevents duplicate entitlement grant (see §9)

## 3. IPN/Webhook Lifecycle

### 3.1 WarriorPlus IPN Format (Assumed)

Based on WarriorPlus's standard IPN specification and industry patterns:

**HTTP Method:** POST
**Content-Type:** `application/x-www-form-urlencoded` or `application/json` (configurable per product)
**Endpoint:** Configured per product in WarriorPlus vendor dashboard

**Key fields:**
```
txn_id              — Unique transaction ID (WPLXXXXXXX format)
buyer_email         — Buyer's email address
buyer_first_name    — Buyer's first name
buyer_last_name     — Buyer's last name
item_id             — WP product/offer ID
item_name           — Human-readable product name
amount              — Total amount paid
currency            — USD, EUR, etc.
country             — Buyer's country
event               — Event type (see below)
status              — Transaction status
cverify             — Verification hash (see §12)
rbin_uid            — Custom param (RobinOS user_id, if preserved)
rbin_email          — Custom param (hashed email, if preserved)
rbin_exp            — Custom param (expiry, if preserved)
rbin_sig            — Custom param (HMAC signature, if preserved)
rbin_ref            — Custom param (referral code, if preserved)
ipn_type            — Instant or delayed
```

**Event types:**
```
SALE               — Initial purchase
BILL               — Recurring billing (for subscription products)
RFND               — Refund (full or partial)
CGBK               — Chargeback
CANCEL             — Cancellation of recurring subscription
CANCEL-REBILL      — User cancelled subscription, no more rebills
UNCANCEL-REBILL    — User uncancelled, rebills resume
PYMT-REBILL        — Payment for rebill
INSF               — Insufficient funds / payment failed
```

### 3.2 RobinOS IPN Handler

**Edge Function:** `warriorplus-webhook` (new)
**verify_jwt:** false (required — IPN doesn't carry user JWT)
**Configuration in `config.toml`:** Add `verify_jwt = false` for the new function

### 3.3 IPN Lifecycle States

The IPN handler moves through these states for each event:

```
RECEIVED → VERIFYING → NORMALIZING → IDEMPOTENCY_CHECK → RESOLVING_IDENTITY
    → RESOLVING_PRODUCT → APPLYING_EFFECT → LOGGING → RESPONDING
```

Each state has explicit success/failure paths.

### 3.4 Lifecycle Flow

#### 3.4.1 RECEIVED
- IPN arrives at the Edge Function endpoint
- Read raw body (required for signature verification)
- Read all headers (especially custom WP headers if any)
- Generate a `trace_id` (UUID v7 for time-ordered debugging)
- Log entry: `{ trace_id, event: 'ipn_received', txn_id, event_type }`
- Record start time for SLO tracking

#### 3.4.2 VERIFYING
- Compute expected `cverify` signature using WP secret
- Compare with provided `cverify` (constant-time comparison)
- **Failure:** log + return 401 immediately. Do NOT process further.
- See §12 for full verification logic.

#### 3.4.3 NORMALIZING
- Parse the body (JSON or form-encoded based on Content-Type)
- Convert to internal `NormalizedWarriorPlusEvent` shape
- See §4 for normalization details
- Validate required fields are present

#### 3.4.4 IDEMPOTENCY_CHECK
- Compute `provider_event_id` = `txn_id + ":" + event_type + ":" + amount`
  - This handles the case where the same `txn_id` has multiple events (e.g. SALE then BILL)
  - Also includes amount to handle partial refunds correctly
- Call `record_webhook_event(provider_event_id, 'warriorplus', event_type, payload_hash)`
- If `is_duplicate = true` → return 200 with `{ received: true, duplicate: true }`
- If `is_duplicate = false` → continue processing

#### 3.4.5 RESOLVING_IDENTITY
- Determine which RobinOS user this purchase belongs to
- See §1.4 for priority chain:
  1. Verify `rbin_sig` + `rbin_exp` → extract `rbin_uid` → confirm user exists
  2. If signed `rbin_email` hash present → lookup by email hash
  3. Match `buyer_email` (lowercase + trim) against `profiles.email`
  4. Fall back to `warriorplus_pending_claims` workflow
- If no match: create pending claim, return 200 (acknowledged but not granted)

#### 3.4.6 RESOLVING_PRODUCT
- Map `item_id` → `plan_key` using **product registry**
- Product registry: a new table or KV-store mapping WP `item_id` → `{ plan_key, billing_cycle, amount, currency, is_subscription }`
- See §12.4 for unknown product handling

#### 3.4.7 APPLYING_EFFECT
- Based on normalized event type, execute the appropriate handler:
  - `SALE` → handleSale (grant plan or create pending claim)
  - `BILL` → handleRebill (extend expiry if subscription product)
  - `RFND` → handleRefund
  - `CGBK` → handleChargeback
  - `CANCEL` / `CANCEL-REBILL` → handleCancellation
  - `UNCANCEL-REBILL` → handleUncancellation
  - `PYMT-REBILL` → handleRebill
  - `INSF` → handlePaymentFailed
- See §5 for entitlement flow

#### 3.4.8 LOGGING
- Write to `subscription_audit_log` with `provider = 'warriorplus'`
- Write to `commission_events` if commission was created/reversed
- Emit `push_admin_notification` for significant events (sale, refund, chargeback)

#### 3.4.9 RESPONDING
- Return HTTP 200 with `{ received: true, status: <processing_status> }`
- **Always return 200** for valid signatures, even if internal processing failed
  - WP will retry non-2xx responses up to N times — this can cause duplicate processing
  - Internal failures are logged + notified, but do not block the WP retry storm
- Return non-2xx only for **signature verification failure** (do NOT retry, log + alert admin)

### 3.5 Retry Behavior

WarriorPlus retries failed IPNs (non-2xx) with exponential backoff for up to **7 days**:
- Retry 1: 1 minute after failure
- Retry 2: 5 minutes
- Retry 3: 30 minutes
- Retry 4: 2 hours
- Retry 5: 12 hours
- Retry 6-10: Daily for 5 days

This means a transient failure (DB outage, network blip) will be retried automatically. The system must be **idempotent** across all retries.

## 4. Payload Normalization

### 4.1 The Normalization Problem

WarriorPlus IPN format is fixed by WP. RobinOS internal events are different:
- WP uses `SALE`, `BILL`, `RFND`, `CGBK`, etc.
- RobinOS internal model uses `subscription.active`, `payment.succeeded`, `payment.refunded`, `payment.failed`, etc.

The IPN handler must **translate** between these vocabularies.

### 4.2 Normalized Internal Event Schema

Every WP IPN is converted into:

```
NormalizedWarriorPlusEvent {
  trace_id: UUID
  received_at: timestamp
  
  // Provider identification
  provider: "warriorplus"
  raw_event_type: "SALE" | "BILL" | "RFND" | "CGBK" | ...
  provider_txn_id: string          // WP txn_id
  provider_event_id: string        // For idempotency: txn_id + ":" + event + ":" + amount
  
  // Buyer
  buyer_email: string              // Lowercased + trimmed
  buyer_name: string               // first + " " + last
  
  // Product
  provider_item_id: string         // WP item_id
  plan_key: string                 // Resolved plan_key (creator, pro_creator, agency, or "unknown")
  billing_cycle: "monthly" | "yearly" | "one_time"
  is_subscription: boolean
  
  // Money
  amount: number                   // Total amount in major units (e.g. 19.00)
  currency: string                 // USD, EUR, etc.
  
  // Identity (RobinOS-side)
  identity_source: "signed_uid" | "signed_email" | "email_match" | "claim_pending" | "unknown"
  user_id: UUID | null             // Resolved RobinOS user_id
  is_new_user: boolean             // True if account created post-purchase
  
  // Affiliate
  referral_code: string | null     // From signed rbin_ref or profiles.referred_by_code
  
  // Raw payload (for audit)
  raw_payload: jsonb
  payload_hash: string             // SHA-256 of raw body
}
```

### 4.3 Event Type Mapping

| WarriorPlus Event | Normalized Effect | Internal Action |
|-------------------|-------------------|-----------------|
| `SALE` | `subscription.activated` (or new purchase) | `safe_plan_switch` (one_time or subscription) + commission creation |
| `BILL` | `subscription.renewed` | `safe_plan_switch` (extend expiry) + commission creation |
| `RFND` | `payment.refunded` | `reverse_commission` + audit log + status update |
| `CGBK` | `payment.chargeback` | `reverse_commission` + manual recovery flag + admin notification |
| `CANCEL` | `subscription.cancelled` | Set `auto_renew = false`, keep access until expiry |
| `CANCEL-REBILL` | `subscription.cancelled` | Same as CANCEL |
| `UNCANCEL-REBILL` | `subscription.uncancelled` | Set `auto_renew = true` |
| `PYMT-REBILL` | `subscription.renewed` | Same as BILL |
| `INSF` | `payment.failed` | Mark `status = 'payment_failed'`, reverse commission if any |
| Unknown | (logged + dropped) | No state change, admin notification |

### 4.4 Subscription vs One-Time Detection

A WP product can be:
- **One-time** (lifetime access, single payment)
- **Subscription** (recurring billing)

Detection methods (in priority order):
1. **Product registry** — has explicit `is_subscription` flag per item_id
2. **Event type** — if WP sends `BILL` events for this txn_id, it's a subscription
3. **Default** — assume one-time unless product registry says otherwise

The product registry is the source of truth. If a WP product is configured as "subscription" but only `SALE` events ever arrive, treat it as one-time (defensive default).

### 4.5 Field Validation

Each IPN must have:
- `txn_id` (non-empty string)
- `buyer_email` (valid email format)
- `item_id` (non-empty string, must exist in product registry)
- `amount` (positive number)
- `currency` (3-letter ISO code, supported: USD, EUR, GBP)
- `event` (must be one of the known event types)

Invalid fields → reject with 400 (before signature check). Valid signature + invalid payload is suspicious — log + alert admin.

## 5. User Entitlement Flow

### 5.1 The Reuse Strategy

RobinOS already has `safe_plan_switch` (migration 31) — the atomic plan-transition RPC. WarriorPlus entitlements will **reuse this RPC** with:
- `provider := 'warriorplus'`
- `provider_sub_id := provider_txn_id` (or a derived stable identifier)
- `amount := payment amount` (in major units)
- `billing_cycle := 'one_time'` for one-time purchases, `'monthly'` for subscriptions
- `triggered_by := 'warriorplus_webhook'`

This requires **NO schema changes** because:
- `user_subscriptions.provider` is `text` (accepts any string)
- `user_subscriptions.billing_cycle` is `text` (accepts `'one_time'` per existing enum)
- `user_subscriptions.amount` is `numeric`

However, `safe_plan_switch` always sets `auto_renew = true`. For WarriorPlus **one-time purchases**, this is wrong. Two options:

**Option 1: Add an optional `p_auto_renew` parameter to `safe_plan_switch`**
- Backward compatible (defaults to existing behavior)
- Adds new parameter `p_auto_renew boolean default true`

**Option 2: Create a new `safe_plan_grant` RPC**
- Wraps `safe_plan_switch` semantics but for grants
- Explicitly handles one-time vs subscription
- More invasive but clearer intent

**Recommendation:** Option 1 — add the parameter. Minimal change, maximum reuse.

### 5.2 Entitlement Grant Flow

When a `SALE` IPN is processed successfully (identity resolved, product mapped):

```
1. Determine plan_key (creator, pro_creator, agency)
2. Determine billing_cycle:
   - From product registry: "monthly" | "yearly" | "one_time"
   - Default to "one_time" for new WP products
3. Determine duration_days:
   - "monthly" → 30
   - "yearly" → 365
   - "one_time" → 365 * 100 (effectively permanent, capped by audit log review)
4. Determine is_revenue_eligible:
   - true if billing_cycle != "one_time" (recurring revenue)
   - false if one-time (one-shot revenue)
5. Determine grant_source:
   - "warriorplus_marketplace" for visibility
   - "warriorplus_direct" if from direct purchase URL
6. Call safe_plan_switch with these params
7. RPC internally:
   - UPSERT user_subscriptions
   - Update profiles.subscription_tier, current_plan, subscription_expires_at
   - Log to subscription_audit_log with triggered_by = 'warriorplus_webhook'
```

### 5.3 One-Time Purchase Handling

A one-time purchase is fundamentally different from a subscription:
- **No recurring billing** — `auto_renew = false`
- **Long or no expiry** — could be lifetime or 1 year
- **No renewal reminders** — `reminder_dismissed_until` irrelevant
- **No cancellation** — nothing to cancel
- **Downgrade on expiry** — if expiry set, expiry flow applies; if lifetime, never expires

Configuration per WP product:
```yaml
WARRIORPLUS_PRODUCT_CREATOR:
  item_id: "wp_xxx"
  plan_key: "creator"
  billing_cycle: "one_time"      # or "monthly"
  duration_days: 36500           # 100 years for "lifetime"
  is_revenue_eligible: false     # one-time revenue, not recurring
  amount_usd: 19.00
```

### 5.4 Subscription Product Handling

If the WP product is configured as recurring:
- Initial SALE grants plan + starts subscription
- Subsequent BILL events extend `expires_at` by 30 days
- CANCEL events set `auto_renew = false` but preserve access
- CANCEL-REBILL ends billing — same as CANCEL
- UNCANCEL-REBILL resumes billing — set `auto_renew = true`

### 5.5 Account Creation for Guest Buyers

If the IPN arrives with `buyer_email` and **no** matching RobinOS account:

**Option A: Auto-create account (less secure, more frictionless)**
- Create `auth.users` row with random password (buyer must reset via email)
- Create `profiles` row with the buyer_email
- Set `email_verified = true` (since they confirmed via WP payment)
- Then grant entitlement
- Send "Your account is ready — set your password" email

**Option B: Require manual claim (more secure, less frictionless)**
- Create `warriorplus_pending_claims` row with claim_token
- Email the buyer a "Claim Your Purchase" link
- No entitlement granted until claimed
- Claim window: 30 days

**Recommendation:** **Option B for security-first MVP**. Option A can be added later for frictionless flow. The audit log captures all attempts, so risk is manageable.

### 5.6 Entitlement Resolution

Once `safe_plan_switch` is called, the rest of the system is unchanged:
- `resolve_user_plan` returns the new plan immediately
- `get_user_entitlements` reflects new limits immediately
- `check_and_increment_usage` enforces new limits immediately
- UI badges and gates update on next page load

The user is **entitled the moment the IPN is processed**. No additional steps required.

## 6. Affiliate Handling

### 6.1 The Double-Commission Problem

WarriorPlus has its own affiliate system:
- Affiliates share WP product links
- WP pays WP affiliates a commission (typically 50-100% of first sale, then 50% rebills)
- WP pays the **vendor** (RobinOS) the net amount (after WP affiliate commission)

**If RobinOS also pays its own affiliates commission on WP-driven sales:**
- The user was referred by **two** affiliates (WP affiliate + RobinOS affiliate)
- Both want their commission
- RobinOS effectively pays the same sale twice (once via WP's reduced payout, once via its own affiliate commission)

This is a real cost — e.g. on a $39 sale:
- WP affiliate gets $19.50 (50%)
- RobinOS gets $19.50
- RobinOS affiliate gets $11.70 (30%)
- RobinOS net: $19.50 - $11.70 = **$7.80**

Without suppression, RobinOS loses 60% of revenue to affiliate stacking.

### 6.2 Recommended Strategy: Suppress RobinOS Commission for WP Sales

**Default behavior:** WP-driven sales do **NOT** trigger RobinOS affiliate commission.

**Rationale:**
- WP already pays its affiliates from the vendor's share
- RobinOS affiliates only earn on direct RobinOS-driven sales (Dodo, Whop, future Stripe)
- This is the standard model for marketplaces — vendors pay marketplace commission, but their own affiliate program only kicks in for direct sales

**Exceptions (future consideration):**
- Could introduce a "RobinOS affiliate override" where WP sales still earn RobinOS commission if the buyer **explicitly** used a RobinOS affiliate link before reaching WP (i.e. `rbin_ref` was set)
- This requires careful accounting but is feasible

### 6.3 Commission Suppression Mechanism

When processing a SALE IPN:

```
1. Detect provider = 'warriorplus'
2. Check if referral_code exists in signed params (rbin_ref)
3. If yes AND admin has enabled "double-affiliate" mode:
   - Create RobinOS commission (treat as normal)
4. Otherwise:
   - Log: "warriorplus sale: skipping RobinOS commission (default behavior)"
   - Do NOT insert into affiliate_commissions
   - Do NOT increment affiliate_profiles balances
5. Always log to subscription_audit_log: 
   - metadata: { wp_affiliate_id, wp_commission_amount, robinos_commission_skipped: true }
```

The "double-affiliate" mode is a **platform_settings** toggle:
- `warriorplus_pays_robinos_affiliate` (boolean, default false)

### 6.4 What Gets Recorded

For **audit and analytics**, every WP sale should record:

```
warriorplus_sales_ledger (new table):
  - id
  - user_id (resolved buyer)
  - warriorplus_txn_id
  - warriorplus_affiliate_id (from IPN, if present)
  - item_id
  - amount
  - currency
  - robinos_commission_skipped: boolean
  - robinos_commission_amount: numeric (if not skipped)
  - created_at
```

This table is **append-only** — used for analytics and revenue reconciliation, never mutated.

### 6.5 Edge Cases

#### User Used RobinOS Referral Link → Clicked WarriorPlus → Bought
- `rbin_ref` is set (the RobinOS affiliate code)
- `rbin_uid` is set (signed)
- IPN contains both
- With default (suppression): RobinOS affiliate does NOT get commission
- Future feature: could earn commission in this case — see §6.2 exceptions

#### User Found WP Listing via WP Affiliate → Bought
- No `rbin_uid`, no `rbin_ref`
- `buyer_email` matches RobinOS user
- WP affiliate gets paid by WP
- RobinOS affiliate does NOT get commission

#### User Bought via Direct URL (no affiliate, no RobinOS link)
- No `rbin_uid`, no `rbin_ref`
- `buyer_email` doesn't match any RobinOS user
- Pending claim created
- No commission to anyone

#### User Already Has Dodo Subscription → Buys on WarriorPlus
- Current behavior (Option 1): Dodo sub is overwritten by WP sub
- **Better behavior:** Detect existing subscription, do not grant duplicate
- Recommendation: **do not overwrite** — return 200 to WP (acknowledged) but log "duplicate subscription attempted"

This requires checking `user_subscriptions` for active subscription from **any** provider before granting:
- If active subscription exists with same plan → return 200, log "duplicate"
- If active subscription exists with different plan → grant the WP plan (allow upgrade)
- If active subscription exists with same provider → return 200, log "duplicate WP purchase"

## 7. Refund Flow

### 7.1 WarriorPlus Refund Events

WP sends `RFND` events for refunds:
- Full refund (amount = original)
- Partial refund (amount < original)

The IPN handler must detect the refund amount and apply accordingly.

### 7.2 Refund Lifecycle

```
RFND IPN arrives
  ↓
[IDEMPOTENCY_CHECK] — same txn_id + "RFND" + amount already processed?
  ↓ (new)
[VERIFYING] — signature valid?
  ↓ (yes)
[RESOLVING_IDENTITY] — find user from original SALE
  ↓
[RESOLVING_PRODUCT] — map item_id to plan
  ↓
[APPLYING_EFFECT — handleRefund]
  │
  ├─ Find user_subscriptions WHERE provider='warriorplus' AND provider_subscription_id = txn_id
  │
  ├─ IF found:
  │    ├─ Determine refund type (full / partial)
  │    ├─ FULL REFUND:
  │    │    ├─ Set user_subscriptions.status = 'cancelled'
  │    │    ├─ Set auto_renew = false
  │    │    ├─ DO NOT immediately revert to free (preserve access until current period ends — matches Dodo behavior)
  │    │    └─ log_subscription_event(refund_full)
  │    ├─ PARTIAL REFUND:
  │    │    ├─ Log the refund but do NOT modify entitlement
  │    │    └─ log_subscription_event(refund_partial)
  │    └─ Reverse commission if any was created (see §6.3 — normally skipped for WP)
  │
  ├─ IF not found (subscription row missing):
  │    ├─ Log "refund for unknown subscription"
  │    └─ Emit admin notification for manual review
  │
  ├─ ALWAYS: push_admin_notification(refund_processed)
  └─ ALWAYS: log_subscription_event(payment_refunded)
```

### 7.3 Refund Safety Window

The existing `reverse_commission` RPC applies regardless of state:
- Pending → reversed (locked_balance deducted)
- Approved → reversed (pending_balance deducted)
- Paid → reversed + requires_manual_recovery (negative available_balance needed)

Since WP-driven sales typically don't create RobinOS commissions (§6.3), `reverse_commission` is usually a no-op for WP refunds. But it should still be called for defense-in-depth.

### 7.4 Partial Refund Strategy

For partial refunds:
- **No entitlement change** — user keeps their plan
- **Revenue note in metadata** — record partial refund in audit log
- **No commission reversal** (if commission was created)

Rationale: A partial refund doesn't invalidate the value the user received. The plan continues.

### 7.5 Full Refund After Period End

If a user refunds AFTER their WP subscription period ended (e.g. monthly sub, paid for Jan, refunds in Feb):
- Subscription is already `expired` or `cancelled`
- Refund still processed
- Commission (if any) reversed
- Audit log captures the late refund

## 8. Chargeback Flow

### 8.1 WarriorPlus Chargeback Events

WP sends `CGBK` events. These differ from refunds:
- Buyer disputes with their bank/credit card company
- WP debits RobinOS's account for the disputed amount + chargeback fee
- Buyer may or may not win the dispute

### 8.2 Chargeback Lifecycle

```
CGBK IPN arrives
  ↓
[Standard IPN processing through VERIFYING → IDEMPOTENCY_CHECK → RESOLVING_IDENTITY]
  ↓
[APPLYING_EFFECT — handleChargeback]
  │
  ├─ Find user_subscriptions WHERE provider='warriorplus' AND provider_subscription_id = txn_id
  │
  ├─ Record chargeback in new warriorplus_chargebacks table:
  │    - id
  │    - user_id
  │    - warriorplus_txn_id
  │    - amount
  │    - chargeback_fee (typically $15-25 — to be configured per WP)
  │    - status: "open" (later: "won", "lost", "closed")
  │    - ipn_payload (full raw for dispute evidence)
  │    - created_at
  │
  ├─ Determine action based on subscription state:
  │    ├─ If active subscription:
  │    │    ├─ Set status = 'cancelled' (immediate — chargeback voids the sale)
  │    │    ├─ Set auto_renew = false
  │    │    ├─ DO NOT revert to free yet — wait for dispute resolution
  │    │    └─ log_subscription_event(chargeback_received)
  │    └─ If already cancelled/expired: just record
  │
  ├─ Reverse commission (if any was created):
  │    └─ This is where requires_manual_recovery flag matters
  │
  ├─ ALWAYS: push_admin_notification(CRITICAL, chargeback_received)
  │
  └─ Audit log with metadata: { chargeback_amount, chargeback_fee, txn_id }
```

### 8.3 Dispute Resolution

WP provides a dispute workflow (typically 60-120 days). WP sends additional events:
- `dispute.won` — RobinOS wins the dispute (buyer was wrong)
- `dispute.lost` — RobinOS loses the dispute (buyer was right)

RobinOS handler:
```
dispute.won:
  - Mark chargeback status = 'won'
  - If subscription was marked cancelled due to chargeback: restore it (call safe_plan_switch again with same params)
  - Push admin notification (info)

dispute.lost:
  - Mark chargeback status = 'lost'
  - Subscription stays cancelled (or reverts to free)
  - Commission reversal stands
  - Push admin notification (warning)
  - Track for analytics (chargeback rate)
```

### 8.4 Chargeback Analytics

Add to platform analytics:
- Total chargebacks (count)
- Chargeback rate (chargebacks / total sales × 100)
- Average chargeback amount
- Win rate (won / lost)
- Total chargeback fees paid
- Affiliate impact (commissions reversed due to chargebacks)

### 8.5 Risk Mitigation

To reduce chargebacks:
- Clear refund policy shown at purchase
- Email confirmation with purchase details
- Easy self-service refund (reduces chargeback incentive)
- 14-day refund window prominently displayed
- Dispute evidence package (auto-generated, sent to WP when CGBK arrives)

## 9. Duplicate Webhook Handling

### 9.1 Why Duplicates Happen

WarriorPlus may send the same IPN multiple times due to:
- Network blip — WP didn't receive RobinOS's 200, retries
- Manual retry from WP dashboard
- Multiple WP servers sending the same event
- Bug in WP retry logic

### 9.2 Idempotency Strategy

**Primary mechanism:** Reuse `record_webhook_event` RPC with provider='warriorplus'.

**Unique constraint:** `(provider, provider_event_id)` from migration 31.

**`provider_event_id` for WarriorPlus:** Computed as `txn_id + ":" + event_type + ":" + amount`

This composite key handles:
- Same txn, same event, same amount → duplicate (idempotent skip)
- Same txn, same event, different amount → different event (partial refund after full refund)
- Same txn, different events → different events (SALE then BILL)

### 9.3 Idempotency Flow

```
1. Compute provider_event_id from normalized event
2. Compute payload_hash = SHA-256 of raw body
3. Call record_webhook_event(provider_event_id, 'warriorplus', event_type, payload_hash)
4. IF is_duplicate = true:
     - Return 200 with { received: true, duplicate: true }
     - Do NOT process further
     - Log: { trace_id, event: 'ipn_duplicate', provider_event_id }
5. IF is_duplicate = false:
     - Continue processing
     - All state changes happen within this branch
```

### 9.4 Race Conditions

If two identical IPNs arrive within milliseconds (parallel processing):
- Both call `record_webhook_event`
- One succeeds (inserts the row)
- The other gets `unique_violation` exception
- `record_webhook_event` catches `unique_violation` and returns `is_duplicate: true`
- Only one processing path continues

This is **already handled** by the migration 31 RPC implementation.

### 9.5 Out-of-Order Events

What if BILL arrives before SALE? (Shouldn't happen but possible due to retries):
- SALE IPN: process → grant plan
- BILL IPN: process → extend expiry (already extended, idempotent UPSERT)

What if RFND arrives before SALE? (Possible during retry storms):
- RFND IPN: try to find subscription → not found → log + notify admin
- SALE IPN: process → grant plan (after admin manually resolves refund)

Edge case: late-arriving RFND after subscription has been cancelled.
- RFND IPN: find subscription → status='cancelled' → just record refund, no state change

### 9.6 Partial Refund + Subsequent Full Refund

Scenario:
1. SALE for $39 → grant pro_creator
2. RFND for $10 (partial) → log, no entitlement change
3. RFND for $29 (remaining) → log, no entitlement change (subscription stays)

Both RFNDs have unique `provider_event_id` (different amounts) → both processed.

If user disputes the **partial refunds** as separate events vs single combined refund:
- WP usually sends one RFND for the total amount, but may send multiple
- Each RFND has its own event ID → processed independently
- Final state: log shows the full refund history

## 10. Error Recovery

### 10.1 Error Categories

| Category | Examples | Handling |
|----------|----------|----------|
| **Transient** | DB connection blip, network timeout | Retry within handler, fail gracefully |
| **Validation** | Missing field, invalid email | Return 400 to WP (no retry needed) |
| **Business logic** | Plan not found, identity unresolved | Return 200 + pending claim + admin alert |
| **Permanent** | Signature failure, schema mismatch | Return 401/400, alert admin |
| **Catastrophic** | DB down, Edge Function crash | WP retries with exponential backoff |

### 10.2 Retry Strategy Within Handler

For transient errors within the handler (e.g. RPC timeout):
- Wrap each stateful operation in a try/catch
- For `record_webhook_event`: retry up to 3 times with 100ms backoff
- For `safe_plan_switch`: retry up to 3 times with 200ms backoff
- For `push_admin_notification`: retry up to 2 times (failures are non-critical)
- If all retries exhausted: return 200 to WP (acknowledged) + emit admin notification with full trace

**Key principle:** Return 200 to WP for ANY processing error that has a valid signature. WP will retry, and idempotency prevents duplicate effects.

### 10.3 Return Code Strategy

```
Signature failure              → 401 (no retry)
Malformed payload              → 400 (no retry)
Identity unresolved (no user)  → 200 (acknowledged + pending claim)
Plan not found in registry     → 200 (acknowledged + admin alert)
DB transient error             → 200 (acknowledged, will retry internally)
Internal logic error           → 200 (acknowledged + admin alert)
Success                        → 200 (received: true)
```

**Why return 200 for "failures"?** Because WP retries non-2xx codes. If the failure is non-recoverable (e.g. user not found), retrying won't help — it just creates duplicate IPNs. Returning 200 acknowledges receipt and lets RobinOS handle the failure via internal alerts.

### 10.4 Pending Claims Recovery

When a purchase has no matching user:
- `warriorplus_pending_claims` row created with claim_token
- Email sent to buyer with claim link
- After 30 days, unclaimed purchases are reported to admin for manual intervention
- Admin can:
  - Manually create user account and link purchase
  - Refund the buyer via WP dashboard
  - Extend claim window (rare)

### 10.5 Database Failure Scenarios

If `safe_plan_switch` fails after `record_webhook_event` succeeded:
- Webhook event is recorded (won't be retried as duplicate)
- State change didn't happen
- **Recovery:** Admin notification with trace_id + manual intervention

If `record_webhook_event` fails:
- Webhook event NOT recorded
- WP retries the IPN
- Next attempt may succeed

If `increment_affiliate_balance` fails (relevant only if double-affiliate mode is on):
- Webhook event IS recorded
- State change happened
- Affiliate balance NOT updated
- **Recovery:** Admin notification + manual balance correction script (rare)

### 10.6 Dead Letter Queue (Future)

For unrecoverable errors, a `warriorplus_webhook_dead_letter` table captures:
- Raw payload
- Trace ID
- Error reason
- Retry attempts
- First seen / last seen timestamps

Admin dashboard can show dead-letter queue and allow manual reprocessing.

### 10.7 Self-Healing Patterns

#### "Already Granted" detection
If a WP BILL event arrives but `safe_plan_switch` finds the user already on the same plan with `expires_at` in the future:
- Do nothing (idempotent)
- Log: "ipn_already_processed_plan_active"
- Return 200

This handles the case where WP sends duplicate BILL events.

#### "Subscription Cancelled" detection
If a WP SALE arrives but the user has an active Dodo subscription:
- Default behavior: WP sale overrides Dodo sub
- **Better behavior:** Detect and log, do not overwrite
- Future: prompt user to choose (requires UI)

### 10.8 Monitoring & Alerting

Key metrics to track:
- IPN volume per hour (alert on anomaly)
- Duplicate rate (alert if > 20%)
- Signature failure rate (alert if > 0%)
- Pending claims count (alert if growing)
- Processing latency p95 (alert if > 5s)
- Error rate by category (alert on any category > 5%)

Admin notifications for:
- Any signature failure
- Any unknown product
- Any pending claim > 7 days old
- Any chargeback received
- Any failed processing > 5 minutes without recovery

## 12. Security Model

### 12.1 Hash Verification

#### WarriorPlus Verification Mechanism (Assumed)

WarriorPlus uses a **verification hash (`cverify`)** computed as:
```
cverify = sha256(api_key + ":" + txn_id + ":" + amount)
```

Or a similar HMAC variant. The exact algorithm must be confirmed from WP's vendor documentation before implementation.

**Note:** This is an **assumption** based on standard IPN patterns. WP may use a different algorithm. The verification function should be designed to be swappable for the actual WP algorithm.

#### Verification Flow

```
1. Read raw body (preserve exactly for hash computation)
2. Extract cverify from payload
3. Recompute expected hash using:
   - api_key (from secrets)
   - txn_id
   - amount
   - + any other fields per WP spec
4. Constant-time compare expected vs provided
5. If mismatch:
   - Log CRITICAL with full context
   - Emit admin notification (security event)
   - Return 401
   - Do NOT process further
```

#### Constant-Time Comparison

Use a timing-safe comparison function to prevent timing attacks:
- Compare byte-by-byte
- Don't short-circuit on first mismatch
- Always process the entire string

### 12.2 Replay Protection

#### Threat
An attacker who intercepts a valid IPN could replay it to:
- Grant duplicate entitlements (mitigated by idempotency)
- Spam the system (mitigated by rate limiting)
- Confuse analytics (mitigated by idempotency)

#### Mitigations

**Layer 1: Idempotency table** — `subscription_webhook_events` with `unique(provider, provider_event_id)`. Replay attempts are detected and skipped.

**Layer 2: Timestamp validation** — Include a timestamp in the signed payload (`rbin_exp` from RobinOS-signed params, or WP's own timestamp field). Reject events older than **24 hours** from current time.

**Layer 3: Nonce tracking** — For maximum security, maintain a `webhook_nonces` table of recently-seen nonces. Reject any nonce that's been seen in the last 24 hours. (Adds DB overhead — only enable if signature verification is weak.)

**Layer 4: Rate limiting** — Limit IPN processing per IP to 100/minute. Excess returns 429 (which WP may interpret as retry-worthy, which is fine — replay attacks shouldn't be at that rate).

**Recommendation:** Layer 1 + Layer 2 (timestamp) are sufficient for WP integration. Layer 3 is overkill for a properly-signed IPN.

### 12.3 Idempotency

#### The Guarantee
**No state change should ever happen twice for the same logical event.**

#### Implementation

**Existing mechanism:** `record_webhook_event` RPC (migration 31) with `unique(provider, provider_event_id)` constraint.

**Composite event ID for WP:**
```
provider_event_id = sha256(txn_id + ":" + event_type + ":" + amount + ":" + timestamp)
```

Using a hash prevents any leakage of the underlying IDs and ensures deterministic generation.

#### Within-Step Idempotency

Even within the handler, operations must be idempotent:
- `safe_plan_switch` — UPSERT pattern (idempotent)
- `increment_affiliate_balance` — uses unique constraint on commission (idempotent)
- `log_subscription_event` — appends (always creates new row)
- `push_admin_notification` — appends (always creates new row; consider de-duplication at admin layer)

### 12.4 Unknown Products

#### The Problem
WP sends an IPN with an `item_id` not in RobinOS's product registry.

#### Handling

```
1. Lookup item_id in product_registry
2. If not found:
   a. Log WARN: ipn_product_unknown
   b. Push admin notification
   c. Create a 'warriorplus_unknown_items' row for manual review:
      - item_id
      - item_name
      - first_seen_at
      - occurrence_count
   d. Do NOT grant entitlement
   e. Return 200 to WP (acknowledged)
   f. Admin must add the item to the registry or escalate
```

#### Self-Healing Mechanism

If the same unknown item arrives multiple times:
- Increment `occurrence_count`
- Send admin notification again with count
- After 10 occurrences, escalate priority to CRITICAL

### 12.5 Unknown Users

#### The Problem
WP sends an IPN for a buyer who is not a RobinOS user and signed params are absent.

#### Handling

```
1. Try identity resolution priority chain (§1.4):
   - Signed rbin_uid
   - Signed rbin_email hash
   - Plaintext buyer_email lookup
2. If no match:
   a. Log WARN: ipn_identity_pending
   b. Create warriorplus_pending_claims row:
      - buyer_email (hashed for PII)
      - buyer_name
      - warriorplus_txn_id
      - warriorplus_item_id
      - amount
      - currency
      - claim_token (UUID v4)
      - claim_expires_at (now + 30 days)
   c. Send email to buyer_email with claim link
   d. Push admin notification (info)
   e. Do NOT grant entitlement
   f. Return 200 to WP (acknowledged)
```

#### Claim Link Flow

```
Buyer receives email:
"Welcome to RobinOS! Click here to claim your WarriorPlus purchase and set up your account."
  https://tryrobin.xyz/warriorplus/claim?token=<claim_token>

Buyer clicks → enters email (re-confirm) → matches pending claim → 
  - Create auth.users account
  - Create profiles row
  - Link pending claim to user_id
  - Grant entitlement (re-run safe_plan_switch with same params)
  - Mark claim as 'claimed'
  - Redirect to dashboard
```

### 12.6 Signature Failure Response

When signature verification fails:
- **Always return 401** (not 200, to prevent infinite retries of bad IPs)
- **Log with CRITICAL priority**
- **Emit admin notification immediately**
- **Include in security metrics**
- **Trigger rate limiting on the source IP**

If signature failures exceed **10 per hour from the same IP**:
- Add IP to temporary blocklist (24-hour TTL)
- Alert admin
- The blocklist is checked before any processing

### 12.7 Secret Management

#### WP API Key
- Stored as Supabase Edge Function Secret: `WARRIORPLUS_API_KEY`
- Same secret used for verification and outbound API calls
- Rotated quarterly (admin procedure)

#### RobinOS Signing Secret
- Stored as Supabase Edge Function Secret: `WARRIORPLUS_ROBINOS_SIGNING_SECRET`
- Used to sign redirect URLs (`rbin_sig`)
- Separate from WP secret for cryptographic isolation
- Rotated annually (admin procedure)

#### Secret Leak Detection
- Edge Function logs **never** include secrets
- Error messages **never** include secrets
- Admin alerts on any log line that looks like it contains a secret (regex detection)

### 12.8 Threat Model

| Threat | Likelihood | Impact | Mitigation |
|--------|-----------|--------|------------|
| IPN spoofing (fake purchase) | Low (signature required) | Critical | Signature verification |
| IPN replay | Medium | Medium | Idempotency + timestamp |
| Identity spoofing (impersonate user) | Medium | High | Signed user_id (HMAC) |
| Affiliate stacking | Low (admin toggle) | Medium | Default suppression for WP sales |
| Subscription overwrite | Medium | Medium | Detect existing active sub before grant |
| Chargeback fraud | Low | High | Dispute workflow + evidence collection |
| Email spoofing | Medium | Medium | Rate limiting + claim workflow |
| Man-in-the-middle | Low (HTTPS) | Critical | TLS + signature |
| Insider attack (admin) | Very Low | Critical | Audit logs + role-based access |
| Denial of service | Medium | Medium | Rate limiting + WP-side retry logic |
| Data exfiltration via logs | Very Low | High | PII redaction in logs |

### 12.9 Compliance Notes

#### PCI-DSS
- RobinOS never touches raw card data — WP handles it
- No PCI scope expansion for RobinOS

#### GDPR
- Buyer email is PII — store hashed, never plaintext in logs
- Claim token expires after 30 days
- Account deletion (existing flow) removes pending claims too
- Right to erasure: pending claims + claim tokens deleted with profile

#### Refund Policy
- Must be clearly displayed at point of purchase
- Standard 14-day refund window
- Disclosed in `/warriorplus` sales page when enabled

## Appendix — Summary of Decisions

| Decision | Choice | Rationale |
|----------|--------|-----------|
| Identity mapping | Hybrid: Signed user_id + email hash + claim token fallback | Balances security and UX |
| Checkout | RobinOS generates signed URL → WP Marketplace checkout | WP owns checkout (marketplace model) |
| Webhook verification | WP's cverify signature + idempotency table | Industry standard |
| Identity in IPN | Signed params (rbin_uid, rbin_email_hash) | Cryptographic strength |
| Claim window | 30 days | Industry standard |
| Plan amounts | Product registry (configurable per item_id) | Avoid hardcoding |
| One-time vs subscription | Determined by product registry | Single source of truth |
| Affiliate commission | Default suppressed for WP sales | Prevent double-payment |
| Refund handling | Status = 'cancelled', preserve access until expiry | Matches Dodo behavior |
| Chargeback handling | Immediate cancellation + dispute workflow | Matches industry best practice |
| Idempotency | Reuse record_webhook_event with provider='warriorplus' | No new infrastructure needed |
| Error recovery | Return 200 + admin alert for internal errors | WP retry logic handles transient issues |
| Logging | 4-layer: Edge logs, audit log, commission events, admin notifications | Reuse existing infrastructure |
| Security | Signature verify + timestamp check + rate limiting + claim workflow | Defense in depth |
| Duplicate detection | (provider, provider_event_id) unique constraint | Migration 31 already provides this |
